Support

Most difficulties fall into a handful of shapes, and they are collected below. When they do not, there is a person at the other end of the address.

Getting in touch

  • Email {{support_email}}
  • Bug reports Open an issue on GitHub
  • Source github.com/russellgordon/plantoir

Email suits a question about how to do something, or a situation that is awkward to describe in public. An issue on GitHub suits a fault that can be described in a sentence and reproduced — it is public, so other teachers meeting the same thing find the answer.

Plantoir is maintained by one teacher alongside a full teaching load. Replies are not instant, particularly in September and in June, but every report is read.

The first day

The first build is taking a very long time. Is it stuck?

Almost certainly not. The first time a site is built, the app assembles the machinery that does the building — several minutes of downloading on a normal connection, and longer on a school network. It happens once. Every build after that starts in seconds.

The progress view names the step it has reached. As long as that wording keeps changing, work is happening.

macOS says the app cannot be opened.

Apps downloaded outside the App Store are checked before they will open. If the warning offers no way past it, control-click the app in Finder and choose Open from the menu that appears, then confirm. This is needed once; afterwards it opens normally.

Move the app to the Applications folder before opening it. Running it from the Downloads folder works, but the app is then thrown away with the next tidy-up.

Does this need an administrator password?

No. Everything the app installs goes inside the user's own Library folder. It is safe to use on a school-managed Mac where administrator rights are not available — though a managed network may block the downloads it needs on first run, which is worth checking with whoever runs it.

Where do the course files actually live?

In a working folder chosen when the app first runs — an ordinary folder, in an ordinary place, with one folder per course inside it. That folder can be opened in Obsidian, backed up, and copied to another computer like anything else.

The working folder must be somewhere inside the home folder. A course kept on an external drive or in a shared folder elsewhere on the disk will appear to be empty when the site is built.

A page is not appearing on the site.

Each page carries an instruction saying which classes may see it, and a page that has not been published to a section is left out on purpose. Ask the assistant what students would see in that section, or open the page and check the settings at the top of it.

If the page is meant to be visible and still is not, rebuild the preview: the site shows the last build, not the current state of the folder.

Publishing failed.

Publishing needs a working connection and, the first time, permission to reach the hosting account. The message shown in the section's window says which of those went wrong.

If the account details were entered wrongly, they can be cleared and asked for again. Nothing about a failed publish changes what students currently see: the site that is already live stays live.

Can a class site be moved somewhere else later?

Yes. The built site is a folder of ordinary web pages, so it can be handed to any host — a school's own web space included. The notes it was built from never leave the teacher's computer, so nothing has to be extracted from anywhere.

Sending a useful report

When something goes wrong, the fastest route to a fix is the report the app makes itself. Choose Report a Problem… from the Help menu. The app asks what to include, saves a file, and shows it in Finder so it can be read before it is sent anywhere.

What it contains

A record of what the app did and when — courses opened, previews built, sites published, and any errors along the way. It is the sequence of events, which is usually enough to identify a fault without asking anyone to reproduce it.

What it never contains

Nothing that was written on a page. No student names, no assessment, no lesson content — the record notes that a page was published, never what the page says. Passwords and account tokens are removed as the record is written, so what is on disk is already safe to hand over.

What is asked before it is made

If sentences have been typed to the assistant, the app asks whether those should be included. They are a teacher's own words, so the answer is theirs to give.

Attach that file to an email, along with what was expected and what happened instead.

Requirements

Mac

macOS 15 or later, on Apple silicon or Intel. A few gigabytes of free disk space for the site builder, plus whatever the courses themselves need.

Windows

A Windows version is built and being prepared for release. It is not available to download yet.

Internet

Needed on the first run, and whenever a site is published. Writing, building and previewing all work offline.

Hosting

A free hosting account, or a folder on a school web server. The app supports both, and switching between them later does not mean rewriting anything.

Privacy

Course notes stay on the computer they were written on. The app has no accounts, collects no analytics, and sends nothing anywhere on its own. A site becomes public when a section is published, and not before.

The assistant runs on the Mac as part of the app. Requests typed to it are not sent to a service and are not used to train anything. It can be left turned off entirely, and the material it needs is only downloaded if it is asked for.

Publishing necessarily involves a hosting provider, and the account details for it are kept in the Mac's own keychain rather than in the course folder.
